# H2: Recognize an item by its photograph

**Status: Implemented** — owner approved the design with browser-side preparation on 2026-09-07. Issue
[#40](https://github.com/mcunille/Workbench/issues/40) originally left the upload,
API/schema, image processing, concurrency, and recovery decisions unapproved; this acceptance resolves those decisions with the changes below.

## Purpose and scope

Attach one optional photograph to a saved individual item, display it in Grid, List,
and details, and allow replacement or removal without deleting or changing the item's
descriptive identity. Follow the accepted [inventory foundation](2026-09-06-inventory-domain-foundation.md)
and [UI guidance](2026-09-06-ui-design-guidance.md).

No multiple-photo library, original-file archive, photo editing/cropping UI, public
sharing, item deletion, or H3/H4 search and descriptive editing ships here. Uploads use
the native file/photo picker; camera capture is available only where that picker offers it.

## Existing implementation and consequences

- `InventoryEndpoints` currently creates and reads items. Its response records expose
  neither photographs nor the existing item rowversion.
- `Collection.tsx` renders neutral placeholders in both collection views and details.
- `AttachmentService` accepts internal generated bytes, publishes one attachment at a
  time, and protects replacement using an expected revision. Its independent transactions
  cannot establish an atomic item reference to two generated images.
- The [provider runbook](../operations/blob-and-service-providers.md) already establishes
  private storage, immutable bytes, integrity checks, seven-day logical-deletion retention,
  holds, pending-operation reconciliation, and paired SQL/blob recovery. Preserve these.

## Photograph policy

| Decision | Proposed behavior |
| --- | --- |
| Input formats | Single-frame JPEG, PNG, and WebP, verified from bytes and full decoding. Reject animation, SVG, GIF, TIFF, HEIC/HEIF, RAW, and other formats with conversion guidance. |
| Input limits | Browser source: at most 20 MiB, 40 million pixels, and 16,384 pixels on either axis. Prepared server upload: at most 4 MiB and 2,048 pixels on either axis. Bound multipart overhead separately; enforce server limits while reading even without Content-Length. |
| Orientation | Apply EXIF orientation before resizing, then remove that metadata. |
| Color | Browser decode and sRGB canvas conversion prepare the source; verify browser behavior with fixtures. Independently convert valid profiles in submitted bytes to sRGB; treat untagged RGB/grayscale as sRGB and reject unprofiled CMYK or unusable profiles at the server boundary. No auto-tone, enhancement, tint, or decorative filters. |
| Detail image | Fit within 2,048 by 2,048 pixels, preserving aspect ratio without upscaling or cropping. |
| Thumbnail | Fit within 384 by 384 pixels using the same orientation and color result. |
| Stored format | Freshly encode both outputs as WebP at quality 90, retaining alpha. Store only a standard sRGB profile if needed, never input profiles or private metadata. Bound the combined encoded outputs to 10 MiB. |
| Privacy | Do not retain original bytes, filenames, EXIF/GPS, XMP, IPTC, comments, or embedded previews in durable storage, logs, or audit records. Explain the original-file policy beside the picker. |

Use Magick.NET Q8 14.17.1 with its Windows/Linux native assets and locked dependencies.
Its upstream [documentation](https://github.com/dlemstra/Magick.NET)
and [color conversion example](https://github.com/dlemstra/Magick.NET/blob/main/docs/ConvertImage.md)
provide the processing basis. Account for the package and native dependency notices.

The server ingestion malware policy is strict raster decoding and reconstruction: incoming
bytes are never served or stored as attachments. Permit only the selected raster coders,
disable delegates, external reads, and network access, and enforce resource limits.
This is not antivirus certification. Decoder vulnerabilities remain a dependency risk.
Do not introduce an external scanner service in H2.

Permit one decoder job per web process, reject excess processing demand with a retryable
503, disable disk pixel-cache spill, cap the native pixel-cache allocation budget at 256 MiB
and threads at two. This is not a hard total-process memory limit. Use cooperative ten-second
progress cancellation and post-processing time checks; upload/storage has the existing
two-minute cancellation deadline. Native decoding cannot be forcibly interrupted in-process.
The approved browser-preparation amendment sharply bounds the input processed by the server;
separate process isolation remains a future hardening option. Verify native policy and the
actual workflow on Windows and the release Linux container without claiming a hard CPU/RSS cap.

## Browser preparation amendment

The browser decodes, corrects orientation, draws into an sRGB canvas, and resizes to a
maximum 2,048-pixel edge before upload. It presents a preview and requires explicit upload.
Prefer WebP only when the returned Blob actually has that media type; fall back to JPEG
for opaque images or PNG for transparency. Reduce output dimensions when necessary to
meet 4 MiB. No failure path uploads the original as a fallback. Browser decode/encoding
and color behavior are verified in supported browser tests, not assumed identical across
devices; this is an identification photograph, not a color measurement or original archive.

The server treats all submitted bytes as untrusted, checks the smaller limits, sanitizes
the normalized image, and derives the thumbnail itself. Full-size camera decoding and
compression therefore occur on the device. Browser re-encoding prevents ordinary uploads
from transferring original metadata; the server independently enforces metadata stripping.

## Persistence and atomic publication

Add `Inventory.ItemPhotoOperations`, tenant-owned and protected by RLS, containing a
server-generated operation identity, item reference, client request UUID, expected item
rowversion, command kind, payload digest, state, actor, timestamps, and the committed
result token. A unique `(TenantId, ItemId, RequestId)` prevents duplicate operations.
The digest binds retries to the exact input bytes, command, and expected version; retain
no original file. Reject reuse with different input as 409.

Add `Inventory.ItemPhotos`, also tenant-owned and protected by RLS, with a server-assigned
photo UUID, item and operation references, detail/thumbnail attachment references, output
dimensions, and creation time. Add nullable `CurrentPhotoId` to `Inventory.Items`.
Use tenant-qualified foreign keys, including item-qualified current-photo membership,
so one item cannot point at another item's photograph. One current pointer enforces one
visible photo. Preserve historical rows for provenance and recovery; expose only current
photos through the item API.

Extend the internal attachment service with explicit preparation and shared-transaction
finalization. Preserve its existing generated-content callers and provider interface.
Photo variants use separate immutable attachment identities with workflow provenance and
`image/webp` media type. Do not expose a generic client-supplied attachment-ID upload API.

1. Authenticate, authorize, enforce antiforgery, and resolve the tenant-owned item before
   decoding or publishing. Validate the request token and bound/read/hash/decode the file.
2. Record the operation and pending variant revisions durably before provider writes.
   Generate both images and stage/publish through `IBlobStore` under server-generated keys.
   Do not hold an item SQL lock throughout decoding or storage I/O.
3. In one short SQL transaction, mark both verified revisions available and insert the
   photo record. Through `Inventory.SetItemPhoto`, atomically compare the rowversion and change
   the current pointer, then record the operation result and audit event. Replacement also
   logically deletes the previous pair and queues its retention jobs in this transaction.
4. Return success only after that transaction commits. Before commit readers continue
   seeing the prior photo; afterward they see the complete new pair.

Removal uses the same expected-version and operation-id rules. Clear the pointer, mark
both attachments logically deleted, enqueue retention work, and record the result in one
transaction. Re-adding later creates a new pair, without resurrecting deleted attachments.

Competing upload/upload and upload/remove operations based on the same item version may
have only one winner. Return 409 for the loser and ask the UI to reload before deciding
whether to retry. Never silently overwrite the winner or change item name/location/notes.
Exact replay of a completed operation returns its recorded outcome without another write;
the UI then reloads current details because a later operation may have superseded it.

## HTTP and authorization contract

Add opaque base64 `version` and nullable `photo` metadata to item detail responses. Add
nullable `photo` metadata to summaries. Metadata includes photo ID, output dimensions,
and same-origin item-scoped thumbnail/detail URLs; expose no physical paths or provider URLs.

| Endpoint | Contract |
| --- | --- |
| `PUT /api/items/{id}/photo` | Multipart `file`, nonempty `requestId`, and `expectedVersion`; returns committed operation outcome and version. |
| `DELETE /api/items/{id}/photo` | JSON `requestId` and `expectedVersion`; returns committed removal outcome and version. |
| `GET /api/items/{id}/photo/{photoId}/{variant}` | `variant` is `thumbnail` or `detail`; resolve the current photo of this item on every request. |

Use existing session authentication, tenant context, and SQL isolation. Photo authority is
inherited from the authenticated inventory membership, and mapped internally to attachment
read/manage authority only after resolving the owned item. Existing generic attachment
service permission checks remain in place. Mutations require antiforgery. Another tenant's IDs, removed/superseded photo IDs,
and mismatched item/photo pairs return 404 without disclosing ownership. Permission failures
follow the existing 403 behavior; expired sessions follow existing 401 handling.

Errors use Problem Details: 400 malformed input, 413 size/pixel limit, 415 unsupported
format, 422 corrupt/undecodable image or unusable color data, 409 concurrency/replay mismatch,
and retryable 503 storage/processing unavailability. Configure request/proxy limits to allow
the specified file plus bounded multipart overhead and verify useful oversized-file errors.
Regenerate OpenAPI and TypeScript declarations.

Image responses use `image/webp`, `X-Content-Type-Options: nosniff`, and `Cache-Control:
private, no-store`. Read each bounded image through the existing integrity wrapper to EOF
before starting a successful response, so digest failure cannot be presented as success.
No anonymous static-file mount, SAS link, original-file download, or historical-photo route.

## Failure, retention, and recovery

Validation or definite pre-commit failure preserves the previous current pointer. An
ambiguous commit is not reported as a definite failed save: the client keeps the same
request UUID, checks current details, and retries the same operation to resolve its outcome.
Do not erase provider objects after an ambiguous database commit.

Record pending state before writing bytes so interruptions can be reconciled. A definitive
concurrency loser with fully published variants can transactionally mark those variants
available but logically deleted and queue seven-day retention. Partial/ambiguous writes
remain pending for the existing offline reconciliation procedure; never guess that a
provider error means an object is absent. Document this operational cleanup requirement.

Logical removal hides delivery immediately; physical deletion follows the existing seven-day
grace and hold checks. Retain audit and digest provenance. Paired backups must include both
variants while retained, and restore verification must block readiness if either required
variant is missing. No production recovery or deployment is authorized by this spec.

## User experience

On saved-item details, show Add photo or Replace photo and an explicit Remove photo action.
Show accepted formats/limits and that original files and location metadata are not retained.
Retain the displayed photo during upload, announce progress/status, prevent duplicate button
submission, and display actionable inline errors with retry. Confirm removal in an accessible
dialog. Protect navigation while an upload is pending and preserve state across theme changes.

Use uncropped images (`object-fit: contain`) on neutral surfaces in Grid, compact List, and
details. Names and locations stay visible without an image; distinguish failed image loading
from an item with no photo and offer retry. Use item-derived alt text where informative and
avoid redundant accessible text in linked cards. Preserve keyboard focus, labeled controls,
44 CSS pixel touch targets, contrast, and no page overflow at 320 CSS pixels.

## Alternatives and tradeoffs

- Original passthrough preserves full fidelity but retains private metadata and untrusted
  content. Reconstructed derivatives prioritize safe display and bounded storage; explain
  that this feature is not an original-photo archive or color measurement tool.
- HEIC support would improve some phone workflows but expands native codec and deployment
  scope. Start with explicit conversion guidance and reconsider based on user demand.
- One full-size image avoids pair finalization but wastes gallery bandwidth. Generate both
  synchronously to avoid an additional background thumbnail readiness state.
- Last-write-wins is simpler but can silently discard another session's photograph. Use
  the existing item rowversion and require an explicit decision after conflict.
- Public blob URLs simplify display but bypass current item/session authorization. Deliver
  through the authenticated application and retain the existing provider portability.

## Migration, verification, and delivery

Use one coherent new migration with tables, constraints, indexes, RLS, web/worker grants,
and schema/readiness changes. Existing items start with no photo. Never rewrite a base
migration. Verify fresh creation and upgrade from the PR base. Reject destructive rollback
once photo records exist; recover through a forward fix or the paired restore runbook.

Write failing focused tests first with GIVEN/WHEN/THEN comments, then implement:

- Decoder fixtures for all accepted formats, orientation, profiled color conversion,
  alpha, metadata stripping, animation, corrupt content, misleading MIME/extensions,
  size/pixel/resource limits, and generated output dimensions.
- Real SQL/API tests for first upload, persistence across sessions, replacement/removal,
  duplicate requests, conflicting payload replay, permissions, antiforgery, cross-tenant
  IDs, direct photo retrieval, and SQL constraint/RLS enforcement.
- Independent-connection races for competing first uploads, replacement/replacement,
  replacement/removal, and exact retries. Inject each variant's stage/publish failures,
  SQL finalization failure, ambiguous acknowledgment, and integrity failure.
- Retention/hold, partial-operation reconciliation, and paired backup/restore drills
  proving both variants are covered, on filesystem and existing Azurite coverage paths.
- Client/browser tests for success, errors/retry, session expiry, conflicts, keyboard,
  removal confirmation, Grid/List/details, reload, mobile widths, and all appearance modes.

Run affected mutation testing and document meaningful surviving mutants and tooling limits.
Run `scripts/verify.ps1` and `scripts/smoke-container.ps1`, plus deployment checks if request
limit/container configuration changes. Inspect the running workflow and update the narrated
Playwright walkthrough with local URLs and accurate evidence. Review the complete change,
