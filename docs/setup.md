# Setup and installation

Start here for a new checkout. Run all commands from the repository root in **PowerShell 7**
(`pwsh`), including on Linux/macOS. This local recipe uses disposable SQL Server Developer edition,
HTTP on loopback, and development certificate trust. Keep valuable data in a separately managed
installation with tested backups; this fixture is not a production database.

## Prerequisites and supported paths

Install .NET SDK **10.0.400**, Node.js **26.7.0**, npm **11.19.0**, PowerShell 7, Git, and Docker
with a running **Linux-container** engine capable of running the pinned SQL Server amd64 image.
An unsupported host architecture is not made supported by these instructions; use a compatible
Linux Docker host. The repository pins are in `global.json`, `.node-version`, and package files.

```powershell
dotnet --version
node --version
npm --version
$PSVersionTable.PSVersion
docker info --format '{{.OSType}}'
```

The last command must return `linux`. On Windows, if Docker is missing from PATH, check both
`C:\Program Files\Docker\Docker\resources\bin` and
`$env:LOCALAPPDATA\Programs\DockerDesktop\resources\bin`. Add the directory containing `docker.exe`
to this terminal's PATH, for example:

```powershell
$env:PATH = "$env:LOCALAPPDATA\Programs\DockerDesktop\resources\bin;$env:PATH"
```

For other missing tools, use `Get-Command dotnet,node,npm,pwsh,git,docker` and check the installer's
per-user location before reinstalling. On Linux/macOS, ensure the installed executables are on PATH
in the `pwsh` session. Restart terminals after installer PATH changes. Do not change repository
version pins to accommodate a different local version.

Local ports are SQL **127.0.0.1:14333** (container 1433), API **localhost:5000**, and Vite
**localhost:5173**. Free these ports before starting; do not stop unrelated containers to free them.
The SQL fixture name `workbench-test-sql` and its port are shared across worktrees on one Docker
engine. Only one checkout should own it at a time.

For installation beyond development, follow the [self-hosted Compose runbook](operations/self-hosted-deployment.md)
or [Azure runbook](operations/azure-deployment.md). These are the checked-in deployment paths.
[Provider issue #11](https://github.com/mcunille/Workbench/issues/11) is closed; provider support is
implemented. [Deployment issue #12](https://github.com/mcunille/Workbench/issues/12) remains open for
hosted acceptance. Public TLS, real SMTP, external SQL certificate validation, the optional production
SQL profile, and full installation recovery require the specific acceptance drills in the
[verification record](operations/deployment-verification.md). Local success does not establish
production readiness. Do not use `.env.dev`, Developer-edition SQL, or this disposable fixture there.

## One-time local setup

### 1. Restore dependencies and start SQL

```powershell
dotnet restore Workbench.slnx --locked-mode
if ($LASTEXITCODE -ne 0) { throw 'Restore failed.' }
npm ci --prefix src/Workbench.Client --ignore-scripts --no-audit --no-fund
if ($LASTEXITCODE -ne 0) { throw 'Client install failed.' }
./scripts/test-sql.ps1 -Action Start
```

`Start` creates a fresh container without a persistent volume. It refuses if that name already
exists. Do not follow its suggestion to stop an existing instance until you have read the
destructive cleanup section below. Check `docker ps -a --filter name=workbench-test-sql` first.

Wait for SQL to accept connections, rather than assuming container creation means SQL is ready:

```powershell
$probe = 'export SQLCMDPASSWORD="$MSSQL_SA_PASSWORD"; /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -C -b -Q "SELECT 1"'
$ready = $false
for ($attempt = 0; $attempt -lt 90; $attempt++) {
    docker exec workbench-test-sql /bin/bash -c $probe *> $null
    if ($LASTEXITCODE -eq 0) { $ready = $true; break }
    Start-Sleep -Milliseconds 500
}
if (-not $ready) { throw 'SQL did not become ready; inspect container status before continuing.' }
```

The password is generated by `test-sql.ps1`. It lives in ignored `artifacts/sql/container.env`
as `MSSQL_SA_PASSWORD`; `artifacts/sql/connection.txt` contains the same credential in a master
connection string. Neither file is a shareable diagnostic artifact. Avoid shell transcripts,
printing file contents, or attaching the artifacts directory to reports. Docker administrators
can inspect the container's environment; use this only on a trusted development machine.

### 2. Create the local configuration without printing secrets

This block refuses to overwrite `.env.dev`. It copies the example in memory, reads the generated
setup credential, generates distinct random passwords and a proof key, then writes the ignored file.
Keep it private to your OS account and this worktree. Do not use a shared or synced directory.

```powershell
if (Test-Path .env.dev) { throw '.env.dev exists; preserve it and use the existing-installation instructions.' }
$setupLine = Get-Content artifacts/sql/container.env | Where-Object { $_.StartsWith('MSSQL_SA_PASSWORD=') }
if (@($setupLine).Count -ne 1) { throw 'Expected one generated SQL setup credential.' }
$settings = Get-Content .env.dev.example
$settings = $settings -replace '^WORKBENCH_SETUP_SQL_PASSWORD=.*$', ('WORKBENCH_SETUP_SQL_PASSWORD=' + $setupLine.Substring(18))
foreach ($name in @('WEB_SQL', 'OPERATOR_SQL', 'MIGRATOR_SQL', 'DEV_ADMIN')) {
    $secret = 'Wb-' + [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(24)) + '-aA9!'
    $settings = $settings -replace "^WORKBENCH_${name}_PASSWORD=.*$", "WORKBENCH_${name}_PASSWORD=$secret"
}
$proof = [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
$settings = $settings -replace '^WORKBENCH_TENANT_CONTEXT_PROOF_KEY=.*$', "WORKBENCH_TENANT_CONTEXT_PROOF_KEY=$proof"
Set-Content -LiteralPath .env.dev -Value $settings
Remove-Variable settings,setupLine,secret,proof
git check-ignore .env.dev artifacts/sql/container.env artifacts/sql/connection.txt
```

All three paths should be reported as ignored. Edit tenant name/email privately before bootstrap
if you want different values. The file is plain `NAME=value`: no shell expressions, quotes, multiline
values, or inline comments. The supplied generated passwords avoid connection-string separators.
For manually chosen passwords, avoid semicolons and quotes because the development scripts compose
connection strings directly. Never put actual passwords in commands or commit them.

| Setting (all names start with `WORKBENCH_`) | Meaning |
| --- | --- |
| `SQL_HOST` | Local host and SQL port, `127.0.0.1,14333` |
| `DATABASE` | `Workbench` for this recipe; the SQL creation command below must match |
| `SETUP_SQL_USER`, `SETUP_SQL_PASSWORD` | `sa` and the generated fixture password; initial migration and principal provisioning only |
| `WEB_SQL_USER`, `WEB_SQL_PASSWORD` | Separate contained runtime user; never use setup credentials for the web process |
| `OPERATOR_SQL_USER`, `OPERATOR_SQL_PASSWORD` | Separate contained user for first tenant/admin and explicit operator actions |
| `MIGRATOR_SQL_USER`, `MIGRATOR_SQL_PASSWORD` | Separate contained user for subsequent explicit schema migrations |
| `TENANT_CONTEXT_PROOF_KEY` | Independent base64 encoding of 32 random bytes; provisioned in SQL and supplied to the runtime |
| `DEV_TENANT_NAME` | Name of the first tenant |
| `DEV_ADMIN_EMAIL`, `DEV_ADMIN_PASSWORD` | Application login identity, not a SQL principal |

`dev-env.ps1` prefers the checkout's `.env.dev`; `WORKBENCH_DEV_ENV_FILE` is a fallback only when
that file does not exist. It derives `WORKBENCH_WEB_CONNECTION` from the web fields. Production
workers and maintenance operations have additional distinct principals and secret mounts; see the
[provider runbook](operations/blob-and-service-providers.md) and deployment runbooks.

### 3. Initialize the empty database and bootstrap

The following command is for the **new disposable fixture only**. It refuses an existing `Workbench`
database, enables server-level contained authentication, creates the database, and sets partial
containment. Principal provisioning needs both containment settings; migration alone is insufficient.
If choosing another database name, have the SQL identifier and `WORKBENCH_DATABASE` changed together;
do not interpolate untrusted names into SQL.

```powershell
$initialize = 'export SQLCMDPASSWORD="$MSSQL_SA_PASSWORD"; /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -C -b -Q "IF DB_ID(''Workbench'') IS NOT NULL THROW 50000, ''Database already exists; inspect it before continuing.'', 1; EXEC sp_configure ''contained database authentication'', 1; RECONFIGURE; CREATE DATABASE [Workbench]; ALTER DATABASE [Workbench] SET CONTAINMENT = PARTIAL"'
docker exec workbench-test-sql /bin/bash -c $initialize
if ($LASTEXITCODE -ne 0) { throw 'Database initialization failed; do not bootstrap until resolved.' }
./scripts/bootstrap.ps1
```

`bootstrap.ps1` applies migrations with the setup connection, provisions web/operator/migrator users
and the proof key, then switches to the operator connection to create the first tenant and administrator.
Passwords travel through temporary files, removed in `finally`, rather than command arguments.
Bootstrap must finish successfully before starting the application. It refuses a second initialized
installation; it is not a routine startup command.

### 4. Start the application and log in

In the API terminal, load configuration, then remove privileged and administrator credentials before
launching the child web process. The loader itself imports all fields, so this filtering matters:

```powershell
. ./scripts/dev-env.ps1
Get-ChildItem Env: | Where-Object {
    $_.Name -like 'WORKBENCH_*' -and
    $_.Name -notin @('WORKBENCH_WEB_CONNECTION', 'WORKBENCH_TENANT_CONTEXT_PROOF_KEY')
} | ForEach-Object { Remove-Item -LiteralPath "Env:$($_.Name)" }
dotnet run --project src/Workbench.Server
```

In a second terminal at the repository root:

```powershell
npm run dev --prefix src/Workbench.Client
```

Open `http://localhost:5173`, use `admin@example.test` (or your configured email), and enter the
generated `WORKBENCH_DEV_ADMIN_PASSWORD` from `.env.dev` using a private editor/password manager.
Do not print it to terminal output. Expect **Welcome to Local Workbench** (or your tenant name),
then reload to confirm the session persists. Sign out and confirm the sign-in form returns.

```powershell
(Invoke-WebRequest http://localhost:5000/health/live).StatusCode
(Invoke-WebRequest http://localhost:5000/health/ready).StatusCode
(Invoke-WebRequest http://localhost:5173/health/ready).StatusCode
```

Expect 200 for each. Liveness alone does not establish database readiness or usable authentication.
The last request verifies the Vite proxy. Local recovery/invitation and blob/worker workflows require
additional provider configuration; they are not enabled by this login-only development recipe.

## Routine startup, updates, and existing databases

Use Ctrl+C to stop Vite and the API. To pause SQL **without deleting data**, use:

```powershell
docker stop workbench-test-sql
docker start workbench-test-sql
```

Run the readiness wait after restart, then repeat only application startup. If the API was left
running during a SQL restart, its first readiness request can fail on a stale pooled connection;
wait for successful readiness before logging in, or restart the API. Container stop/start
retains its writable layer; container deletion does not. `test-sql.ps1 -Action Status` reports
existence, not SQL health or whether the container is running. Use `docker ps -a` for state.

After pulling changes, repeat locked restores/`npm ci` when lockfiles change. Back up retained data
before an update, inspect the release's schema requirements, stop incompatible writers, then run
`./scripts/migrate.ps1` from a separate operations terminal. It uses only the migrator connection
for SQL migration. Restart the app and repeat readiness/login checks. Do not re-run bootstrap or
regenerate passwords/proof keys on an initialized installation.

For an existing managed SQL database, preserve its credentials and backup first. An authorized DBA
must arrange contained authentication and database containment before principal provisioning.
Do not run the disposable creation command or point this fixture's `sa` credential at another server.
Follow the [migration runbook](operations/database-migrations.md) for explicit file-based tooling.
Use validated SQL certificates outside this local fixture.

The original identity baseline has shipped; the old blanket “unmerged baseline” caveat no longer
applies. Databases made from earlier, unmerged PR revisions may still have rewritten migration
history (including pre-consolidation provider migrations). Such databases are not supported upgrade
baselines. Preserve needed data and plan an explicit transition, or opt into a fresh disposable
installation. Never edit migration-history rows to pretend an upgrade succeeded.

## Destructive cleanup and partial failures

**`./scripts/test-sql.ps1 -Action Stop` deletes the container and all databases in its writable layer,
then deletes `artifacts/sql`, including the generated credentials. It is not a service stop.** Use it
only after explicitly deciding every database in that fixture is disposable or safely backed up.
It does not remove `.env.dev`; that file becomes stale when a replacement fixture generates a new
setup password. Archive any needed configuration privately before deliberately recreating it.
Do not run `docker compose down --volumes` to restart an installation.

For valuable data, follow [paired backup and restore](operations/database-backup-restore.md), including
blob data and data-protection keys where configured. An ignored directory is not a backup. Keep backups
outside the fixture and verify restoration before deletion. Restore authentication sanitation is mandatory.

| Failure | Recovery |
| --- | --- |
| Container name/port already used | Identify its owner; resume your existing fixture or choose a separate managed setup. Do not delete unknown data. |
| SQL startup timeout | Check Docker engine/resources and container state. Review SQL diagnostics privately; never publish environment inspection or credential files. |
| SQL login fails | Check host port, generated setup credential source, database name, and whether `.env.dev` belongs to a replaced fixture. |
| Contained authentication error | Confirm both server authentication and database partial containment with the DBA; do not repeatedly retry bootstrap without fixing this. |
| Initialization stopped after creating the database | Inspect that database and set its containment through an authorized SQL session; the guarded creation command intentionally refuses retries against an existing DB. |
| Migration/provisioning failed before tenant creation | Preserve the error without secrets, inspect schema/principals using the runbook, correct the cause, then retry bootstrap only if the installation is still uninitialized and credentials/key are unchanged. |
| Bootstrap reports already initialized | Use the existing administrator login; do not recreate the tenant or reset the database. A lost admin password requires the documented controlled recovery process. |
| Readiness returns 503 | Confirm SQL is running, migrations are current, runtime uses the web user, and proof key matches provisioning. Check configured provider health too. |
| Login fails but readiness succeeds | Check application email/password rather than SQL passwords; use the same `localhost` browser origin and allow any rate-limit cooldown. |
| Process interrupted during setup | Temporary credential files may survive forced termination under the OS temp `workbench-bootstrap-*` directory; remove only files belonging to that stopped attempt. Preserve SQL until its state is understood. |

## Automated verification

Stop the local API with Ctrl+C first; on Windows it can lock build output needed by verification.
Keep Docker running. The verification fixtures create their own disposable SQL environments.
Before the first browser test run, install the locked test package and Chromium:

```powershell
npm ci --prefix tests/Workbench.BrowserTests --ignore-scripts --no-audit --no-fund
if ($LASTEXITCODE -ne 0) { throw 'Browser test dependency install failed.' }
node tests/Workbench.BrowserTests/node_modules/@playwright/test/cli.js install chromium
if ($LASTEXITCODE -ne 0) { throw 'Browser install failed.' }
```

On Linux, install Playwright's OS dependencies using its `install-deps chromium` command with
appropriate package-manager privileges before running browser tests. Reinstall the browser when
the pinned Playwright version changes.

```powershell
./scripts/verify.ps1
./scripts/smoke-container.ps1
```

The first gate checks pinned tools, locked restores, docs, formatting, generated API drift, builds,
server/client tests, real SQL migration drills, browser login/session behavior, and published output.
The second builds and exercises the container/Compose runtime. Both require Docker for complete
coverage. The verification script installs npm packages; it does not install browser binaries or
OS dependencies. If the browser executable is missing, repeat the explicit browser installation above.

After a successful dependency install with unchanged lockfiles, `./scripts/verify.ps1 -SkipDependencyInstall`
reuses `node_modules`; it still performs locked .NET restore and current-source builds. NuGet/npm
caches can reduce downloads but do not replace lock validation. Do not use old `--no-build` results
as evidence for changed source. Record versions, fresh setup outcomes, readiness/login, and unavailable
gates in the implementation PR, without credentials, cookies, or secret artifacts.
